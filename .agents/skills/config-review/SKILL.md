# $config-review

タスク変更全体を3観点でレビューし、結果を統合して報告する。報告のみで、修正は行わない。

## 制約

- 読み取り専用。ファイルの編集・作成・削除、およびGitの状態変更(add/commit/checkout/reset/stash/push等)は禁止。このMarkdown自体は権限を変更しない。実行側で読取専用sandboxと承認なし(never)を設定し、変更可能な外部ツールも無効化する。設定できない場合はレビューを開始せず未完了と報告する。
- Bashを使う場合はGit読取コマンド(`git status` `git diff` `git log` `git show` `git ls-files` `git merge-base` `git rev-parse` `git merge-base --is-ancestor`)に限る。これは運用上の指示であり、完全なsandboxや拒否境界ではない。
- 親は対象の確定と統合を担当する。3観点は独立した子agentに各1回だけ委譲し、全結果を待つ。同じ観点を3周しない。
- 実行側のモデル・推論量・読取専用条件を確認して報告する。ユーザー指定があればその指定を使い、なければ実行セッションの設定を継承する。指定モデルや推論量が使えない場合は勝手に別の値へ置き換えず未完了とする。不明な実効値は不明と書く。
- 子agentにも同じモデル・推論量と読取専用条件を適用する。skillの読込だけでは子agent起動や権限制御にならない。委譲機能や読取専用条件が用意できなければ該当観点を未完了とし、親による代行を独立レビューと数えない。

## 1. 対象の確定

対象は「合意された起点から最終worktreeまで」のタスク変更全体。次をすべて含める。

- 起点以降の全taskコミット
- staged の変更
- unstaged の変更
- 未追跡の新規ファイル(`git ls-files --others --exclude-standard`)

ignoredファイルとsecrets(`.env`、鍵、認証情報等)は含めない。内容も読まない。

### 起点(`<base>`)を固定SHAに解決する

比較元ブランチが進んでも無関係な差分を含めないため、起点は常に固定SHAとして解決し、以降の全コマンドでその同じSHAを使う。

- 比較元(ブランチ/タグ/リモート追跡ref等)が指定された場合: `git merge-base <比較元> HEAD` の結果SHAを `<base>` とする。比較元の先端そのものは使わない。
- 明示commitが合意した起点として指定された場合: `git merge-base --is-ancestor <commit> HEAD` でHEADの祖先であることを確認し、祖先であれば `git rev-parse <commit>` で得たそのSHAを `<base>` とする(merge-baseで置き換えない)。祖先でなければ曖昧として扱う。
- 比較元/起点が渡されていない、曖昧、または解決できない(refが存在しない、merge-baseが得られない、祖先でない等)場合: 最小の質問を1つだけして待つ。`main` や直近コミットへ自動で代替しない。
- leadから要件と起点が渡されていればそれを使う。
- 1コミットやHEADだけを対象にしてはならない。

解決した `<base>` のSHAと、その由来(比較元名またはcommit指定)を報告に記す。

## 2. 収集(順序を守る)

以下の `<base>` は、手順1で解決した固定SHAと必ず一致させる。

1. 先に変更ファイル名だけを列挙する: `git diff --name-only <base>`、`git log --oneline <base>..HEAD`、`git ls-files --others --exclude-standard`。
2. 列挙結果から、機密(`.env`、鍵、認証情報、secrets類)とignoredを除き、読む対象を明示パスに確定する。除外したパスは名前だけ報告する。
3. 確定した明示パスに限って差分(`git diff <base> -- <path>...`)と未追跡ファイルの内容を読む。パス指定なしの `git diff <base>` 全文は取得しない。
4. 要件(引数・会話・leadの指示から。不明なら不明と明記)と、適用規約(`rules/coding.md` 等、存在する規約ファイル)を集める。

## 3. 3観点の実行

次の3つのskillを、独立した子agentが1つずつ読んで実行する。呼出側は会話履歴に依存しない入力を渡し、結果を待つ。

- `config-review-correctness`
- `config-review-tests`
- `config-review-design`

各skillへは、要件・解決済みbase(固定SHA)・対象範囲(確定した明示パス一覧と除外パス名)・差分・適用規約の全文を、その呼出だけで自己完結するよう渡す。差分が大きい場合も、明示パス一覧とbase SHAは必ず渡し、各観点が関連コードを自分で読めるようにする。

## 4. 統合と報告

- 3観点すべての結果を受け取ったことを確認する。失敗・未完了・空の結果、または要件/base/規約の不足で判断できなかった観点は「未完了」と明記し、レビュー完了や「問題なし」「指摘なし」と報告しない。再試行ループは行わない。
- 重複する指摘は1つにまとめ、どの観点から出たかを併記する。
- 根拠が弱い、または差分・コードで確認できない指摘は誤検出として除外し、除外理由を一行で示す。
- 問題を無理に作らない。

出力形式:

```
## 対象
base(固定SHAと由来) / 範囲 / 除外パス名 / 観点ごとの完了状況

## 指摘
[P0|P1|P2] path/to/file:行 — 内容
  根拠: ...
  最小修正案: ...

## 除外した指摘
...
```

指摘がなく全観点が完了していれば、完了した観点を明記したうえで「指摘なし」と書く。

優先度: P0=壊滅的または緊急のリスク(データ損失、重大な脆弱性、即時の障害)、P1=重大な正確性/安全性の問題や要件の阻害、P2=任意の改善。一般的なバグを全てP0にしない。
