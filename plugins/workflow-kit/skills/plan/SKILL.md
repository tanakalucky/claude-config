# Plan

Plan も文書化も必要に応じた任意の工程である。すべての変更に計画ファイルや承認の儀式を
要求しない。[develop](../develop/SKILL.md) のパターン 1・2 では不要。
シンプルさの方針は develop に従う。

## 会話上の Plan（パターン 3）

会話で短く示す: 目的、範囲と対象外、進め方、検証と受け入れ条件、要判断点。
ユーザーが既に合意済みなら再確認しない。未合意の重要な判断があれば実装前に確認し、
質問は箇条書きにする。

## 文書化した Plan（パターン 4）

対象 repo の既存の計画規約に従う場所へ文書化する。なければ `docs/plans/<短い名前>.md` に置く。
プラグイン内へ repo 固有の計画を保存せず、他の変更の計画を
上書きしない。lead の Write / Edit はこの計画文書だけに使う。
計画に認証情報、個人情報、生の環境出力を書かない。

項目は最小限にする: 目的・完了条件・対象外／タスクと順序／検証・受け入れ条件／
重要な判断と理由。機械的なチェックリストは求めない。

## Plan レビュー

独立した reviewer 1 名（workflow-kit:design-rules-docs-reviewer）が 1 回だけ、
実現可能性・妥当性、過剰設計、抜け漏れを確認する。実装レビューのラウンドとは別枠であり、
実装レビューの回数に含めない。渡す資料や制約は [review](../review/SKILL.md) の
レビューの根拠に従う。

指摘は Plan に反映する。重大な指摘が残る場合は、自動で再レビューを繰り返さず
ユーザーに相談する。
