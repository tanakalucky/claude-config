# 実装レビュー

対象は [develop](../develop/SKILL.md) のパターン 2・3・4 の実装レビューである。
Plan レビューの手順は [plan](../plan/SKILL.md) を参照する。

## レビューの根拠

reviewer へは、機密情報を除去したレビュー資料を渡す。資料には必要な範囲に限定して
次を含める: 範囲、関連する差分と必要な周辺、関連する規約・README の抜粋と出典、
検証結果、既知の不足。差分全体やファイル全文を無確認で複製しない。
秘密情報、認証情報、環境ダンプ、本番ログ、個人・ユーザーデータ、無関係なファイルは
含めない。reviewer はこの資料だけを読み、生のソースや README は、パスを指定されても
直接読まない。機密情報を除去した資料ファイルの正確なパスを渡すのはよい。
資料の作成は implementer に依頼し、lead が委任前に内容を確認する。
ハッシュや予約トークンによる照合は要求しない。ただし reviewer に渡した後に
レビュー対象を変更したら、その変更は未レビューとして扱う。

reviewer は Read のみ・omitClaudeMd の読み取り専用で、シェルやソース編集の権限を持たない。
提供された資料だけを読む。

## レビューの種類

- 通常の実装レビュー（パターン 3・4）: workflow-kit:security-reviewer、
  workflow-kit:test-adequacy-reviewer、workflow-kit:design-rules-docs-reviewer の
  別々の 3 名を可能なら並列に起動する。3 観点そろって 1 ラウンドとする。
  その場限りの追加レビュー担当は起動しない。
- 軽量レビュー（パターン 2）: design-rules-docs-reviewer 1 名に 3 観点すべてを依頼する。
  1 名による 3 観点であり、独立した 3 名ではないと報告する。

## 重大度とラウンド上限

- P0/P1 は修正して再検証が必要。P2 は任意であり、追加ラウンドの理由にしない。
  根拠不足は blocked であり、問題なしではない。
- 実装レビューは 1 つの変更につき最大 3 ラウンド。回数は lead が数えて報告するもので、
  機械的に強制されるものではない。失敗・中断したラウンドも数え、回数をリセットしない。
- P0/P1 の修正後は、残りのラウンドの範囲内で再レビューする。レビューが必要な最終的な
  変更が未レビューのまま残っている場合は、完了と呼ばない。
- 3 ラウンド後に重大な問題（P0/P1、失敗したレビュー、検証不足、未レビューの必須の修正）が
  残る場合は、4 回目へ進まずユーザーに相談し、承認済みと表現しない。ユーザーが別の上限や
  レビュー方法を明示した場合はそれに従う。

問題なしの結果を捏造しない。レビュー結果はマージやデプロイの許可ではない。
