# アーキテクチャを相談する

メインの会話で Opus の lead として進める。ユーザーの依頼は $ARGUMENTS であり、
シェルコマンドへ展開しない。調整に専念し、コードや文書の編集は
workflow-kit:implementer に委任する。Opus を利用できない場合は報告して止める。
このスキルはインストール、公開、マージ、デプロイ、データ共有の許可を与えない。

最初に [README の共通方式](directory-readme.md) と
[開発ワークフロー](../develop/SKILL.md) を読み、それぞれの読み方・権限境界と
レビューの扱いに従う。必要な確認は lead の読み取りか implementer が行う。

## 進め方

1. 対象範囲、達成したいこと、変えないもの、必要な制約・受け入れ条件を整理する。
   既に決まっている判断と、今回相談する判断を区別する。
2. 共通方式に沿って必要な README の経路を読み、既存の構成・依存・テストを確認する。
   対象プロジェクトの具体的な設計を根拠にし、一般論だけで構成を決めない。
   調査を implementer に委任する場合は、問い、必要な祖先を含む範囲、終了条件を渡す。
3. 要件を満たす少数の候補を示す。現状維持や最小変更で足りるなら、それも候補にする。
   各案の責務の分け方、依存の向き、置くもの・置かないもの、移行・保守・テストへの
   影響を比較し、推奨理由と未解決点を簡潔に伝える。
4. ユーザーと相談し、採用案と実行範囲を確認する。案の提示や調査を実装承認と
   みなさない。承認前はファイル移動、コード変更、構成用の空ディレクトリ作成、
   未承認の設計の README への確定記載を行わない。
5. 承認された判断を、共通方式に従う階層の README へ記録するよう implementer に
   委任する。子間のルールは共通の親、各子の詳細はその子が所有する。
   決定理由と承認範囲を必要な箇所に短く残す。将来の案は確定した規約と区別する。
   文書化だけの承認でコードを移動しない。構成変更も承認された場合は、影響する
   README の更新と実装・検証を同じ develop の変更として進める。
6. 文書だけの変更も develop のレビュー工程で検証し、承認内容と実装・文書が
   一致することを確認する。採用案、更新ファイル、検証結果、保留した判断を報告する。
